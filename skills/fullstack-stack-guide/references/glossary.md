# 全栈术语表

用法：术语首次出现在选型对话里时，用四段式讲。

1. **专业词** —— 用户之后可以拿去跟别人对话的「暗号」
2. **一句白话** —— 不需要背景知识也能懂
3. **为什么影响你** —— 绑定当前项目的具体后果，不作通用定义
4. **常见误用** —— 用户最容易踩的那个坑

不要一次倾倒全部。只解释影响当前决策的术语。

## 架构与形态

**前后端分离**：
页面跑在浏览器里，数据从另一台机器上的服务拿。
**为什么影响你**：多一个要部署、要监控、可能会挂的单元，出问题时你要判断是页面还是服务的问题。
**常见误用**：以为「分离」只是把代码分两个文件夹——它指的是两个独立的运行单元。

**单体（monolith）**：
一个应用包含前端、后端、数据访问，跑在一起。
**为什么影响你**：所有逻辑在一个进程里，改一处影响全局，但调试和部署简单。
**常见误用**：把「单体」当成落后。团队小、需求杂时单体通常更快。

**全栈框架自带 server**：
框架（Next.js / TanStack Start）内部就有服务端逻辑，不用单选一个后端框架。
**为什么影响你**：少一个独立部署单元，但服务端代码的边界由框架划定，绕不开它的约定。
**常见误用**：以为这样就没有后端——服务端代码、鉴权、数据访问一样都在，只是换了位置。

**微服务**：
把系统拆成多个独立部署的服务。
**为什么影响你**：每个服务都要独立部署、监控、跨服务调试；用户规模不大时纯成本。
**常见误用**：为了「架构好看」拆。第一次做产品基本不需要。

## 网络与接口

**HTTP / REST**：
一套请求-响应约定。REST 是其中一种风格：用 URL 表示资源、用 GET/POST 等动词表示操作。
**为什么影响你**：前后端之间的对话方式。REST 简单、什么语言都能调；别的风格更类型安全但工具链更专。
**常见误用**：以为 REST 就是「GET 拿数据 POST 改数据」。真正决定难易的是状态码、错误格式、分页约定是否统一。

**RPC（远程过程调用）**：
像调本地函数一样调远程接口。
**为什么影响你**：类型能跟着接口走，前端调后端时参数和返回值有编译期检查。
**常见误用**：以为 RPC 就是「换个 URL 写法」。RPC 的收益在类型共享，不在调用形式。

**OpenAPI**：
一份描述接口形状的规范文件，机器可读。
**为什么影响你**：能自动生成文档、自动做客户端、给第三方接入。
**常见误用**：以为写了 OpenAPI 就等于有 API 文档——它需要额外的渲染与托管。

**tRPC / oRPC 这类「端到端类型安全」方案**：
前后端共享一份接口定义，类型自动同步。
**为什么影响你**：改接口时前端立刻报编译错，不用等联调。
**常见误用**：以为它只省事。它会约束你的接口设计——比如所有接口都得走同一套约定。

**中间件（middleware）**：
在请求到达处理逻辑之前/之后跑的一段通用逻辑（鉴权、日志、限流）。
**为什么影响你**：所有请求都要过这里。中间件顺序错了，鉴权可能在日志之后、限流可能在解析之后。
**常见误用**：把业务逻辑塞进中间件，最后中间件变成一坨什么都能干的函数。

**SSR（服务端渲染）**：
页面在服务器上生成好再发给浏览器。
**为什么影响你**：首屏更快、对搜索引擎更友好，但服务器要承担渲染开销，且要处理两套环境（服务端没有 `window`）。
**常见误用**：以为 SSR 一定更快。慢查询在 SSR 下会更慢，因为用户等的是服务器。

**CSR（客户端渲染）**：
页面在浏览器里生成。
**为什么影响你**：服务器只发空壳，渲染负担给用户浏览器；首屏可能白一下。
**常见误用**：以为 CSR 一定慢。数据已在浏览器缓存时，CSR 的重复导航更快。

**API 契约**：
前后端约定的「这个接口收什么、返回什么、什么情况报错」。
**为什么影响你**：这是前后端之间的法律条文。契约模糊，联调时全靠猜。
**常见误用**：只写成功路径。错误契约（错误码、错误消息格式）比成功路径更容易扯皮。

## 数据层

**数据库 / DB**：
存数据的地方。
**为什么影响你**：决定数据能存多大、能扛多少并发、能不能做复杂查询、以及数据丢了怎么办。
**常见误用**：把「用哪个数据库」当成纯技术偏好。数据敏感性和备份要求往往是决定性的。

**SQL**：
跟关系型数据库说话的语言。
**为什么影响你**：慢查询、索引设计、事务问题都得靠 SQL 知识定位，ORM 不会替你解决。
**常见误用**：以为用了 ORM 就不用懂 SQL。

**ORM**：
让你写 TypeScript/Python 而不是手写 SQL 的中间层。
**为什么影响你**：表结构改了之后，迁移脚本能不能自动生成、能不能回滚，取决于它。
**常见误用**：以为 ORM 让你不用设计表结构——它只是把你的设计翻译成 SQL。

**迁移（migration）**：
记录「表结构从哪个版本变成哪个版本」的脚本。
**为什么影响你**：改表结构是生产事故的高发区。迁移能不能自动生成、能不能回滚、能不能在不停服的情况下做，直接影响上线风险。
**常见误用**：开发时直接改数据库不改迁移文件。上线时生产库和开发库结构不一致。

**Schema**：
数据的结构定义（有哪些表、字段、关系）。
**为什么影响你**：它是你产品数据的骨架。schema 改一次，迁移、API 契约、前端类型都要跟着动。
**常见误用**：在 schema 里塞业务逻辑。

**索引**：
数据库为加速查询建的辅助结构。
**为什么影响你**：查询慢绝大多数是索引没建对。索引不是越多越好，写入会变慢。
**常见误用**：给每个字段都加索引。

**事务**：
一组操作要么全成、要么全不成。
**为什么影响你**：涉及钱、库存、余额的地方必须靠事务保证不出错。
**常见误用**：以为事务能包住所有问题。事务只管数据库，不管外部调用。

**连接池（connection pool）**：
数据库连接是稀缺资源，池子负责复用。
**为什么影响你**：池子太小，高并发时请求排队；太大，压垮数据库。
**常见误用**：忘了设池上限，直接用框架默认值。

**NoSQL / 文档数据库**：
不强制固定表结构，存「文档」形态的数据。
**为什么影响你**：schema 灵活，适合结构不定的数据；但复杂查询和跨文档关系弱于关系库。
**常见误用**：以为 NoSQL 一定更快。快慢取决于访问模式，不取决于有没有 schema。

## 后端与运行时

**运行时（runtime）**：
真正执行你代码的环境。
**为什么影响你**：决定你的代码能用什么 API、能不能用并发模型、部署形态长什么样。
**常见误用**：把运行时和语言混为一谈。同一门语言在不同运行时上能力不同。

**ASGI / WSGI**：
Python 里定义「Web 服务器怎么调用你的应用」的两种标准。
**为什么影响你**：选 WSGI 框架（如 Flask）就用不了 FastAPI 那套 async 依赖注入和 async ORM；选 ASGI 才能。
**常见误用**：以为装了 uvicorn 就自动兼容所有框架。框架必须明确支持该协议。

**事件循环（event loop）**：
单线程里靠调度实现并发的机制。
**为什么影响你**：CPU 密集任务（图像处理、大量加解密）会堵死整个服务，因为它不是为这个设计的。
**常见误用**：在 async 函数里调同步的阻塞函数（如同步 HTTP 请求、文件读写），把整个服务卡住。

**WSGI / ASGI 服务器**：
真正跑你的 WSGI/ASGI 应用的进程（gunicorn、uvicorn、granian）。
**为什么影响你**：开发时能跑不等于生产能跑。生产的并发模型、进程数、超时设置都在这一层。
**常见误用**：开发用内置服务器，生产也用它。

**进程 vs 线程**：
进程有独立内存，线程共享内存。
**为什么影响你**：多进程内存隔离但不能共享状态；多线程共享内存但有竞态。这决定你怎么放全局缓存。
**常见误用**：以为多核性能问题靠加线程就能解决——Python 的 GIL 让纯 Python CPU 任务无法靠线程并行。

**后台任务 / 队列**：
把耗时的活丢到后台慢慢做（发邮件、生成报表、调第三方 API）。
**为什么影响你**：用户请求不该等这些活。需要队列系统（Celery / Dramatiq / Taskiq 等），也就多一个要部署、要监控的东西。
**常见误用**：在请求里同步等结果，用户等十秒，接口超时。

**幂等**：
同一个操作做多次和做一次结果一样。
**为什么影响你**：队列会重试、网络会重发。没有幂等设计，重复扣款、重复下单就是这么来的。
**常见误用**：以为「请求返回成功」就等于「只执行了一次」。

## 认证与安全

**认证（authentication）**：
确认「你是谁」。
**为什么影响你**：决定谁能进系统。选错代价很大——过松则数据泄露，过严则用户流失。
**常见误用**：把「有登录」当成「有认证」。登录页存在不等于会话管理正确。

**授权（authorization）**：
确认「你能做什么」。
**为什么影响你**：认证之后的所有越权问题都在这层。多租户系统里，「用户 A 能不能看到用户 B 的订单」是授权问题。
**常见误用**：只在前端隐藏按钮就算做了权限控制。前端隐藏是界面，后端不校验就是漏洞。

**会话（session）**：
服务端记住「这个请求来自已登录用户」的机制。
**为什么影响你**：决定登录状态存在哪（服务端数据库 / cookie / token）、怎么过期、怎么踢人下线。
**常见误用**：以为 JWT 天然比 session 好。JWT 无法即时撤销，适合无状态服务；session 便于撤销，适合有状态后台。

**Cookie / Token / JWT**：
三种传递「已登录」这个状态的方式。
**为什么影响你**：决定跨域限制、能否即时登出、移动端与桌面端行为是否一致。
**常见误用**：把 token 放 localStorage 就以为安全了——XSS 能读走。

**CSRF / XSS**：
两种经典攻击：CSRF 借你的身份发请求，XSS 在你的页面里注入脚本。
**为什么影响你**：决定了 Cookie 该不该带 `SameSite`、输入要不要转义、token 存哪。
**常见误用**：只防了其中一个。

**输入校验**：
在信任边界上检查数据形状与范围。
**为什么影响你**：这是防注入、防越权的第一道闸。跳过它，后面所有防线都得独自承担。
**常见误用**：只在前端校验。

## 前端

**组件（component）**：
可复用的界面单元。
**为什么影响你**：决定界面怎么拆、状态怎么归属、复用机会在哪。
**常见误用**：组件里塞数据请求，导致同一个数据在多处重复请求。

**状态管理**：
决定「数据放在哪、谁负责同步」。
**为什么影响你**：状态放错地方（比如全局）会引发无谓的重渲染与耦合。
**常见误用**：把所有状态塞进全局 store，哪怕只有一层组件用。

**服务端状态 vs 客户端状态**：
服务端数据（列表、详情）与界面状态（弹窗开没开）是两回事。
**为什么影响你**：两者用不同工具管。混着管会出现「缓存不同步」这类怪问题。
**常见误用**：把服务端数据复制进全局 store，然后两份数据不一致。

**客户端渲染的 hydration**：
服务端渲染的 HTML 到浏览器后，React 重新接管并绑定事件。
**为什么影响你**：服务端和客户端渲染出的内容不一致时，hydration 会报错或丢交互。
**常见误用**：在组件里直接读 `window` 或用 `Date.now()`，服务端和浏览器结果不同。

**Tailwind / CSS-in-JS / CSS Modules**：
三种样式方案。
**为什么影响你**：影响样式复用方式与构建产物大小。
**常见误用**：以为工具选型影响不大——它会在项目变大后明显影响开发速度。

**组件库（shadcn/ui 等）**：
现成的无样式组件，代码直接进你的仓库。
**为什么影响你**：能省大量时间，但样式与行为要自己改，改动成本要算进去。
**常见误用**：以为「复制进仓库」就等于完全可控——后续每个组件都要自己维护。

## 数据与合规

**个人数据（personal data）**：
能直接或间接识别到具体自然人的信息——姓名、邮箱、手机号、身份证号、地址都算。
**为什么影响你**：决定了这一层能不能用托管的第三方服务（数据出境、数据留存）、要不要加密、要不要留审计日志、备份要保留多久。用户说「有客户联系方式」就是在说这一层。
**常见误用**：以为「内部系统」就不受约束。内部系统里存着个人数据，约束一样在。

**数据最小化**：
只收集业务真正需要的数据。
**为什么影响你**：字段越少，泄露影响面越小，合规成本越低。选型时影响要不要引入用户画像、分析表、第三方同步。
**常见误用**：先全存下来，以后可能用得上。

**审计日志（audit log）**：
记录谁在什么时候做了什么操作，且记录本身不被随意修改。
**为什么影响你**：数据出错或被误改时，唯一的追溯手段就是它。要不要建这层、存在哪、谁能看，是选型时要定的。
**常见误用**：只记业务日志（谁调用了接口），不记数据变更（谁把这条记录改了）。

**备份与恢复**：
定期复制数据，且验证过真的能恢复。
**为什么影响你**：决定你敢不敢改数据、敢不敢上生产。「有备份」和「备份能恢复」是两件事——后者要实际演练过。
**常见误用**：以为云盘自动同步就是备份。误删会同步过去。

**加密（静态加密 / 传输加密）**：
数据落盘前加密、传输中用 TLS。
**为什么影响你**：影响数据库选型与密钥管理方式。自建数据库与应用层加密的责任在谁身上，要提前分清。
**常见误用**：以为用了 HTTPS 就不用管静态加密。两件事。

**合规（compliance）**：
外部规则对系统提出的硬性要求。
**为什么影响你**：合规要求会**推翻**技术偏好——比如要求数据不出境，会直接排除某些托管服务，这时不能靠「生态惯例」去解释。
**常见误用**：把合规当上线前才检查的事。它应该在选型阶段就进前提。

## 工具链与工程

**构建工具（build tool）**：
把源码变成能部署的东西。
**为什么影响你**：开发时的热更新速度、产物大小、部署方式都由它决定。
**常见误用**：只看「能不能构建」，不看增量构建与 HMR 快不快——这才是日常体验。

**monorepo**：
一个仓库装多个包。
**为什么影响你**：跨包改代码不用发版，但也意味着一套工具链管所有包，配置复杂度上升。
**常见误用**：项目还只有一个的时候上 monorepo。

**锁文件（lockfile）**：
记录每个依赖的确切版本。
**为什么影响你**：团队与 CI 装出来的依赖一致，不会「我这儿能跑你那儿不能」。它必须提交进版本控制。
**常见误用**：用范围版本（`^1.2.3`）装生产依赖而不带锁文件。

**peer dependency**：
声明「我需要你装某个兼容版本」。
**为什么影响你**：peer 版本范围不满足时，依赖树会冲突或运行时报错。这是组合不兼容最常见的来源。
**常见误用**：忽略 peer 警告强行 `--force` 安装。

**类型检查（typecheck）**：
静态验证类型是否匹配。
**为什么影响你**：很多错误在跑起来之前就能被拦住。这是投入产出比最高的一道防线。
**常见误用**：把类型错误当噪音关掉。

**lint / formatter**：
统一代码风格与抓低级错误。
**为什么影响你**：风格统一让 review 与协作变快。
**常见误用**：规则没配好，噪音大到大家开始整体忽略。

**CI**：
每次提交自动跑一遍检查。
**为什么影响你**：把「本地能跑」变成「合并前必然验证过」。
**常见误用**：CI 里只跑测试不跑类型检查与 lint。

## 部署与运维

**容器（container）/ Docker**：
把应用连同依赖打包成可复现的运行环境。
**为什么影响你**：解决「我这儿能跑你那儿不行」。但它引入了镜像构建、镜像大小、编排这些新概念。
**常见误用**：把镜像做得巨大（塞进编译工具链与源码），拉取慢且有攻击面。

**镜像（image）**：
容器的模板。
**为什么影响你**：镜像里有几个 Python/Node 版本，直接决定你的运行时版本。
**常见误用**：用 `latest` 标签导致镜像内容随时间变化，构建不可复现。

**编排（orchestration）**：
管理多个容器实例的调度与伸缩。
**为什么影响你**：单机不用管，服务多实例时才需要。Kubernetes 对小项目是过度工程。
**常见误用**：为了「以后要扩容」第一天就上 K8s。

**Serverless / 边缘运行时**：
按请求计费或跑在离用户更近的地方。
**为什么影响你**：省掉服务器管理，但有执行时长、文件系统、依赖包大小等限制，且冷启动有延迟。
**常见误用**：忘了这些限制，把一个 30 秒的同步任务塞进请求里。

**CI/CD / 部署流水线**：
自动构建并发布。
**为什么影响你**：决定「改一行代码到用户看到」要多久，以及发布是否可回滚。
**常见误用**：没有回滚路径——出问题时只能现场改。

**健康检查（health check）**：
服务定期自报是否可用。
**为什么影响你**：编排系统靠它判断实例是否该重启。没有它，故障实例会一直挂着。
**常见误用**：只检查进程活着，不检查依赖（数据库）是否可用。

**可观测性（日志 / 指标 / 链路追踪）**：
让你在出问题时能看见发生了什么。
**为什么影响你**：没有它，故障排查靠猜。这在生产环境的价值远高于开发期。
**常见误用**：只记成功路径，出错时日志里什么都没有。

**回滚（rollback）**：
把线上版本退回上一个可用版本。
**为什么影响你**：决定了出事的代价。有回滚路径，事故是分钟级；没有，是小时级。
**常见误用**：以为「数据库迁移不可逆」就无法回滚——迁移本身要设计成可逆或向前兼容。
