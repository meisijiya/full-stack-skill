# 全栈技术栈选型指导

给一个全栈项目选出**能跑、彼此兼容、且用户能理解**的技术栈组合，并在过程中把术语讲清楚。

## 边界

**做**：选型、候选比较、组合兼容性判定、版本兼容查证、术语解释、开发中因需求变更而评估「继续 / 降级 / 换栈」。

**不做**：需求澄清与需求拷打对齐、架构设计、写代码、代码审查。这些交给对应技能。

判据：如果一件事的答案不取决于「选哪套技术」，它就不属于本技能。

## 何时用

- 用户说「我要做个 X 系统，用什么技术栈」「Drizzle 和 Prisma 选哪个」「这个组合能跑吗」
- 用户对全栈术语不理解，或在用与工程侧不同的含义（「接口」「前后端」「部署」「迁移」）
- 已有选型的项目里需求变了，可能要换栈或砍功能
- 需要查某个库当前该用哪个版本、某个版本组合是否兼容

## 三条铁律

1. **版本号一律现查现证。** 本技能不含任何版本号。查法见 `references/version-verification.md`。每次选型都要把命令与输出写进 `docs/stack/version-evidence.md`。
2. **区分「技术硬约束」与「生态惯例」。** 官方文档证实的不兼容才是硬约束；脚手架或社区的常见搭配不是。混淆二者会让用户为一个本可保留的功能付出降级代价。判定标准见 `references/constraints-typescript.md` 与 `references/constraints-python.md` 的分层说明。
3. **给排序候选组合，让用户选。** 不替用户拍板，不只给一个默认栈。每个候选组合给出理由与代价。

## 流程

### 阶段一 · 锁定选型前提

只问**会改变选型**的硬事实，不做需求梳理。每个问题都直接影响某一层的候选集。

必问项（缺一项就问）：
- 部署目标与运行环境（自有服务器 / 云托管 / 边缘 / Serverless）
- 数据规模、并发量、数据敏感性（是否涉及个人信息、是否需要审计）
- 团队既有技能（决定上手成本，往往是决定性因素）
- 必须对接的外部服务（支付、IM、地图、第三方 API——它们常常直接决定 SDK 与运行时）

按需追加：预算与时间线、是否要桌面端/移动端、是否需要多租户、是否需要离线。

把这些问题一次性问完（用宿主的提问机制；没有就用普通提问列表），每题给「无偏好 / 不关心」出口。

**完成标准**：拿到足以把候选集收窄到 2–3 套的硬事实。仍无法收窄时，明确说明缺哪条事实、缺它会导致什么分歧，然后按最保守假设继续并标注该假设。

### 阶段二 · 给候选组合 + 解释术语

读 `references/constraints-typescript.md` 或 `references/constraints-python.md`（按用户语言选轨），用其中的层候选与约束表生成 2–3 套**完整**候选组合——每套覆盖所有层，不留空。

每套组合必须给：
- **每层选型**（具体到库，不是「某个 ORM」）
- **理由**：为什么它匹配阶段一的前提
- **代价**：这套的短板、放弃的东西、未来的天花板
- **排序依据**：哪条前提决定了它排第一

**术语解释**（首次出现某个术语时用四段式，取自 `references/glossary.md`）：
1. 专业词
2. 一句白话
3. **为什么它影响你** —— 绑定到当前项目的具体后果，不是泛泛定义
4. 常见误用

例（ORM）：
> **ORM** —— 让你写 TypeScript/Python 而不是手写 SQL 的中间层。
> **为什么影响你**：表结构改了之后，迁移脚本能不能自动生成、能不能回滚，取决于它。
> **常见误用**：以为用了 ORM 就不用懂 SQL。索引和事务的问题照样要靠 SQL 知识定位。

不要一次倾倒全部术语——只在影响用户当前决策的术语上解释。

**完成标准**：用户拿到 2–3 套可比较的完整组合，每套的取舍用他自己的话能复述。

### 阶段三 · 出决策表并落盘

用户选定后：

1. 按 `references/artifacts.md` 的格式写 `docs/stack/decision.md`（决策表）、`docs/stack/version-evidence.md`（版本查证记录）。
2. 在使用方项目的 `AGENTS.md` 追加 stack 小节，指向 `docs/stack/decision.md`。先检查是否已有该小节，避免重复添加。
3. 告知用户：决策表在哪、什么时候该复核（建议每个大版本或需求变更时）。

版本查证在写决策表**之前**做：候选组合定下后，逐层跑查证命令，把命令、输出、日期写进 `version-evidence.md`。查不到官方兼容声明的层，标「未查得官方声明」，别假装确定。

**完成标准**：三个文件已写入使用方项目，`AGENTS.md` 已指向决策表，用户知道下一步是什么。

## 开发中复核

需求变更可能撞上选型前提时启动：

1. 读 `docs/stack/decision.md`，找出被触及的层。
2. 给出三个选项，每个都写明代价：
   - **继续**：不动这层，代价是什么
   - **降级**：保住架构但砍掉部分功能，砍掉什么、用户会失去什么
   - **换栈**：换这一层，迁移工作量、什么会重写
3. 用户选定后，把结论追加进 `docs/stack/change-impact.md`（新开一份，不覆盖历史）。

复核只评估选型影响，不动手改业务代码。

**完成标准**：三个选项的代价已摊开，用户选定并记录在案。

## 常见失误

- 凭记忆给版本号 → 必须现查，本技能没有版本表
- 把脚手架偏好说成硬约束 → 参考 `vibestart` 那类矩阵时尤其容易犯；本技能的两层分类是为此设的
- 候选组合留空层（「数据库用合适的那个」）→ 每层必须具体
- 术语倾倒 → 只解释影响当前决策的
- 用户已经懂的东西反复解释 → 判断依据是「这个术语是否影响他这次的决策」
